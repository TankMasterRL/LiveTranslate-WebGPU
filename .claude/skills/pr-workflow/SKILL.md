# PR workflow

These are the actions to perform when shepherding a PR end-to-end.
Follow them in order; skip steps only when the user explicitly
declines them.

1. **Branch.** Start from an up-to-date `main`
   (`git checkout main && git pull origin main`), then create the
   `claude/<topic>-<suffix>` branch the task specifies.
2. **Implement + validate.** Red/green TDD: write the failing test
   first. Keep changes focused on a single pipeline stage or module
   where possible; edits to shared seams (`PipelineDeps`, the worker
   message protocol, cue-timing semantics) are cross-cutting and must
   call out the blast radius. Gates before pushing: `bun run test`
   (includes the real-model Silero integration test), `bun run check`,
   `bun run test:e2e`, and `bun run build` — plus a
   `BASE_PATH=x bun run build` when touching asset or model URLs, and
   `bun run screenshot` (commit the regenerated `docs/screenshot.png`)
   when the change alters the web UI's appearance.
   Changes to Whisper/translation inference paths additionally require
   the manual WebGPU verification steps in the README (CI has no GPU).
   Use the commit-message conventions above, including the
   `Assisted-by:` trailer.
3. **Push.** `git push -u origin <branch>`. Retry with exponential
   backoff (2s / 4s / 8s / 16s, up to 4 attempts) on network failures
   only.
4. **Open the PR only when asked.** PRs target
   `tankmasterrl/livetranslate-webgpu` — the GitHub MCP tools in this
   environment are scoped to that repo and calls elsewhere will be
   denied. Use a short imperative title and fill in the
   [PR description template](#pr-description-template) below.
   **The agentic harness may
   auto-append a `_Generated by [Claude Code](...)_` footer to the PR
   body — always strip it immediately after creation via
   `update_pull_request`, as it violates the no-session-links rule
   above.**
5. **Subscribe to PR activity automatically** via
   `subscribe_pr_activity` immediately after the PR is opened — don't
   wait for the user to ask. Investigate review comments; make small
   fixes directly, ask the user when ambiguous. The PR-merged webhook
   unsubscribes on its own. CI (`.github/workflows/ci.yml`: check,
   unit, e2e) must be green before merge; manual WebGPU verification
   remains the bar for inference changes.
6. **Keep the test plan up to date continuously.** Update the PR body
   via `update_pull_request` after _every_ event that changes the
   status of a checklist item — don't batch updates to the end.
   - **Check completed:** tick the box and note how it was verified,
     e.g. `- [x] \`bun run test\` green — validated on \`abc1234\``
   - **New commit pushed to the branch:** review every previously-ticked
     item; if the commit touches code that the item covers, un-tick it
     and annotate with `(re-opened by \`<sha>\`)` so the reviewer knows
     it needs re-verification on the new head.
   - **Item not exercised in this PR:** mark it
     `- [ ] <item> — N/A: <short reason>` rather than deleting it, so
     the scope of the PR remains visible to reviewers.
7. **Merge only on explicit request.** PRs are squash-merged via
   `merge_pull_request` with `merge_method: squash`. Write the squash
   commit title as the final imperative subject; put the body detail
   in the squash commit message. The `Assisted-by:` trailer must
   appear in the squash message.
8. **Clean up.** Once a PR has been merged, **all branches belonging
   or previously belonging to that PR must be removed** — the PR's
   head branch on the remote (`git push origin --delete <branch>`),
   its local counterpart and any local worktree branches, and any
   superseded branches from earlier iterations of the same PR (e.g.
   after a rename or retarget). A merged PR must leave no stale
   branches behind.

### PR description template

Every PR body has a `## Summary` section and a `## Test plan`
checklist, in that order. The summary may grow whatever structure the
change needs — bullets per change area, a root-cause narrative,
subsections, a closing "Notes for the reviewer" — but the two
top-level sections are always present. Start from this skeleton:

```markdown
## Summary

<!-- What changed and why, as prose and/or one bullet per change area.
     Bug fixes: quote the observed symptom (the exact error message if
     there is one), explain the root cause, then the fix.
     Features: what was added and the key design decisions (which seam
     it plugs into, why a dedicated worker, model/file provenance).
     Call out the blast radius explicitly when a shared seam changes
     (PipelineDeps, the worker message protocol, cue-timing semantics).
     Mention doc updates (README, CLAUDE.md) and anything investigated
     but deliberately left unchanged. -->

## Test plan

- [ ] `bun run test` green — validated on `<sha>`
- [ ] `bun run check` clean — 0 errors / 0 warnings on `<sha>`
- [ ] `bun run test:e2e` green — validated on `<sha>`
- [ ] `bun run build` green — validated on `<sha>`
- [ ] `BASE_PATH=x bun run build` green — validated on `<sha>`
- [ ] CI green (`Dockerfile.test` container: check + unit incl. the
      real-model Silero integration test + e2e) — `test` job succeeded
      on `<sha>` (link the run)
- [ ] `bun run screenshot` — regenerated PNG committed (or
      byte-identical, nothing to commit)
- [ ] Manual WebGPU verification — <concretely, what to check in a
      real browser>
```

Filling it in:

- **Every item stays in the list.** Tick what was verified and say
  how (``— validated on `<sha>` ``, with pass/skip counts); mark
  inapplicable items `— N/A: <short reason>` instead of deleting them
  (typical: `BASE_PATH` build when no asset/model URLs changed;
  screenshot when the UI's appearance is unchanged; manual WebGPU
  verification when no inference path is touched; the code gates on a
  docs-only change).
- When the sandbox blocks huggingface.co, the real-model Silero tests
  self-skip — note the skip count and that CI's Docker image exercises
  them, rather than reporting a bare pass count.
- Manual WebGPU verification is **required** whenever an inference
  path changes (CI has no GPU) — spell out concretely what the
  verifier should observe, not just "verify manually".
- Keep the checklist live per workflow step 6: tick items as they
  validate, re-open ticked items when a new push touches what they
  cover, never batch updates to the end.
